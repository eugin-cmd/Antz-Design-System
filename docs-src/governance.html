Who can change the official system

The GitHub repository is the only source of truth. Everyone can use the system and its agent; only the System Owner approves and publishes changes. Instructions to an AI are not access control: GitHub enforces it with read-only access for everyone else, .github/CODEOWNERS and the rulesets in .github/rulesets/ (main can't be deleted or force-pushed; release tags v* are created only by the owner and never move). AI agents build and audit products and prepare changes when asked; they never approve, release or deploy on their own.

Proposing a change (RFC)

  1. Copy governance/rfc/TEMPLATE.md to governance/rfc/RFC-NNN-short-name.md.
  2. Describe the need, the alternatives you checked (search the system first), the tokens and components affected, accessibility impact and the change class.
  3. A maintainer triages it weekly. Minor: maintainer and platform lead approve. Major and Foundational: the council, then the System Owner.
  4. Accepted RFCs become decision records and changelog entries.

Exceptions

When a standard truly doesn't fit, a team can deviate on the record. Every exception names its files and rules and has an expiry date. The check honours it until then, and fails once it expires.

  1. Submit: the requirement, the module and screens, the rule it departs from.
  2. Alternatives: why existing tokens and components can't do it.
  3. Review: design and technical review by a maintainer.
  4. Accessibility: the Accessibility Lead signs if any accessibility property changes.
  5. Decision: approved or rejected with reasons, recorded in governance/exceptions.json.
  6. Expiry: default six months, with an owner who reviews it.
  7. Promotion: if three or more modules need the same exception, it becomes an RFC. An exception never silently becomes a standard.
