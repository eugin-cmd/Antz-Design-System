Two tiers: Development and Published

Improvements happen in Development and never reach a product on their own. A product only changes when it moves its pinned version.

Development (evolution)
  • The repository root: tokens/src, components.css, docs, the theme tester.
  • Experiment with treatments, themes, motion and new components.
  • Every commit runs the gates (pre-commit hook).
  • Products never link it.
Published (stable)
  • releases/vX.Y.Z/: a full copy of the system at that version.
  • Immutable: every file has a SHA-256 in MANIFEST.json; any edit fails release --verify.
  • Tagged in Git (vX.Y.Z) with a changelog entry.
  • Products pin one version and upgrade when ready.

The promotion path

  1. Developbranch or working copy; RFC for anything beyond a fix
  2. Reviewdesign, technical and accessibility review
  3. Validatebuild, contrast gate, guardrail check, self-tests
  4. Approveby change class (patch, minor, major, foundational)
  5. Releasenode tools/release.mjs freezes, checksums and tags
  6. Publishedproducts pin it; docs list it under Versions

For designers

You keep working the way you do now: one web codebase for web, tablet and mobile prototypes. Only the stylesheet link changes.

  1. Link a pinned release in every prototype (never the working copy):
    <link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter:wght@300..700&display=swap">
<link rel="stylesheet" href="antz-design-system/releases/v1.2.0-beta.10/tokens.css">
<link rel="stylesheet" href="antz-design-system/releases/v1.2.0-beta.10/components.css">
  2. Build with classes first (.btn--primary, .card, .status--caution, .wash--primary). Each component page shows them.
  3. Write your own CSS with tokens only: var(--color-*), var(--space-*), var(--text-*), var(--radius-*), var(--duration-*), var(--ease-*), var(--gradient-*).
  4. Check before you share: node antz-design-system/tools/check.mjs path/to/your-prototype. It lists every break with the rule and line.
  5. Try ideas in the theme tester, not in a prototype: light, dark, high contrast, compact, every device size.
  6. Need something new? Propose it (RFC). If a module truly needs to differ, request an exception; it expires and is reviewed.

Changing the system

  1. Open an RFC for anything beyond a fix (governance/rfc/TEMPLATE.md). Foundational changes (brand colour, typeface, principles) need the System Owner.
  2. Edit the source: tokens/src/** for values, components.css for components, docs-src/ and pages/_nav.json for docs.
  3. node tools/build.mjs: validates tokens, runs 724 contrast checks in 4 modes, writes every output. It fails on any error.
  4. node tools/check.mjs and node tools/test.mjs: guardrails and their self-test.
  5. node tools/audit.mjs: the rendered audit in Chrome. Every colour token in all 36 combinations of OS and page settings, every text element on every page in four modes (measured on real pixels), reduced motion, links and tap targets. Run it before every release.
  6. Commit. The pre-commit hook re-runs the gates and refuses stale generated files.
  7. Add a CHANGELOG.md section, bump VERSION (patch, minor or major), commit, then node tools/release.mjs.

Going back to an earlier version

  • A product: change its pinned path back, e.g. releases/v1.0.0-beta.1/. Nothing else moves. A rollback never changes another product.
  • Browse an old version: open releases/vX.Y.Z/index.html, or pick it on Versions and releases.
  • The whole source: node tools/rollback.mjs 1.2.0-beta.4 shows what would change; add --yes to restore that release as a new commit, after the gates pass. History is kept, and git revert HEAD undoes it.
  • The live site: node tools/deploy.mjs --list shows every deploy; --rollback <id> puts an earlier one back live in seconds. See Going back.

AI coding assistants

Assistants follow the same rules as people, and the same checks catch them. AGENTS.md (and the short CLAUDE.md adapter) point any tool at the rules. Nothing depends on one AI vendor.

Working with the system

Do
  • Link a pinned release in prototypes and products.
  • Use classes first, tokens second.
  • Run the check before sharing work.
  • Propose new tokens and components through an RFC.
  • Upgrade one product at a time and read the changelog first.
Don't
  • Link the repository root from a product.
  • Edit tokens.css, colors.json or dist/ by hand: they are generated.
  • Edit anything inside releases/.
  • Copy hex values into your CSS.
  • Ship a deviation without an exception record.

Commands

# build tokens and every output (fails on invalid tokens or contrast)
node tools/build.mjs

# guardrails: this repo, or any prototype or product folder
node tools/check.mjs
node tools/check.mjs ../my-prototype
node tools/check.mjs ../antz-dashboard/src --report

# prove the guardrails work
node tools/test.mjs

# docs: render docs-src and refresh nav on every page
node tools/docs.mjs

# publish the version in VERSION (frozen, checksummed, tagged)
node tools/release.mjs
node tools/release.mjs --verify     # nothing published has changed
node tools/release.mjs --list       # published versions

# serve the docs and theme tester locally
python3 -m http.server 8092 --bind 127.0.0.1
